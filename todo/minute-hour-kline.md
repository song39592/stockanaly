# 后期待办：评估 时线 / 分线（小时 · 分钟级）K 线实现

> 本条原文为「评估时和分K线实现」，按 **「评估（研究）小时级与分钟级 K 线的实现方案」** 理解；
> 若原意是别的（例如「评估时点」概念），请更正本文。

## 背景
**当前 K 线只支持日 / 周 / 月，无小时、无分钟**：
- 周期枚举：`backend_fastapi/core/periods.py:23` `PERIODS = ("day", "week", "month")`；
  `normalize()` 非此三者直接抛错 — `periods.py:26-31`。
- 周 / 月是**读取时现算**（日线是唯一落库口径）— `periods.py:2-17`；`resample_bars()` — `periods.py:84`。
- 合样唯一出口：`backend_fastapi/core/kline_service.py:82` `get_bars(..., period="day")`（`:59` 调用 `resample`）。
- 个股历史接口：`backend_fastapi/features/history/routes.py:61-72`（`normalize` 在 `:15 / :67`）；
  服务层 `features/history/service.py:274-307`（`period != "day"` 才合样）。
- 前端周期切换：`launcher/StockPoolLauncher.cs:605-615`（`F8` 循环 日→周→月→日）。

**数据源现状：只有日线**：
- `backend_fastapi/core/price_store.py:98` `CREATE TABLE daily_bars`，按年份分片库 `db.bars_db(year)`（`:251`）。
- 全仓搜 `分钟` / `minute` / `1m` / `5m` / `15m` / `tick` / `日内`：**无一处处于 K 线周期语境**
  → **无分钟表、无分钟接口、无分钟数据源**。

## 目标
评估并落地「时线（60m）与分线（1/5/15/30m）」的 **数据源 → 落库/合样 → 接口 → 前端周期** 整条链路；
先产出一份**数据源可行性结论**（这是最大变量），再决定是否投入实现。

## 具体步骤
1. **数据源评估（最关键，先做）**——候选：
   - (a) 现有日线数据源（akshare 等）是否提供分钟历史？回溯深度多少、限流多严？
   - (b) 自建本地分钟库（`minute_bars` 表 + 分片 + 定时增量拉取，长期累积）；
   - (c) 实时/准实时（仅盘中，历史仍要落库）。
   给出各方案的回溯深度、限流、存储成本、更新方式。
2. **扩展周期枚举**：`periods.py` 增加 `1m/5m/15m/30m/60m`（或 `min` 前缀），`normalize()` 支持；
   确认 `resample_bars()` 能从分钟合样到小时/日（复用同一套）。
3. **存储**：仿 `price_store.py` 新增分钟表与分片策略，定义每日增量更新任务。
4. **服务 / 路由**：`kline_service.get_bars` 支持分钟周期；`features/history/service.py` 合样分支覆盖 分钟→小时。
5. **前端**：`StockPoolLauncher.cs:605-615` 周期循环加入分钟 / 小时档；
   K 线渲染层确认能承载更大数据量（分页 / 懒加载）。
6. **与回测/评估衔接**：明确分钟级是否进入回测（数据量、撮合假设），以及「评估」在分钟粒度下的口径。

## 验证
- 单票拉取各分钟周期：根数、时间戳单调、无缺口（对齐交易日历与盘中时段 9:30–11:30 / 13:00–15:00）。
- 分钟→小时、分钟→日 合样结果与数据源原生小时线对比一致。
- 前端切换周期渲染正确、无卡顿。

## 风险 / 注意
- **高**：数据源是硬约束——免费源分钟历史深度有限且有限流；要长历史必须自建累积库（存储 + 更新成本）。
- 盘中时段 / 停牌 / 除权处理易错。
- 工作量明显大于其他三项，**建议先出「数据源可行性结论」再决定是否动手**。
