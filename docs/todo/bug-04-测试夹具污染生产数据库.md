## 根因（完整因果链）

1. **第 27 项（core/ 搬家）首跑的兼容转发写的是 `from core.X import *`（复制名字）**。
   测试 `setUp` 里 `db.DATA_DIR = 临时目录` 的重绑打在**副本**上，
   实现模块（`core.price_store` 等）仍读真实数据盘 ——
   **那次跑出的 26 个失败里，夹具数据直接写进了用户的真实分片库**。
2. 随后改成 `sys.modules` 别名转发重跑全绿 —— **但坏那次写入的行没人清理**
   （重跑用的是临时目录，碰不到已落进真实库的旧行）。
3. 污染行（`source=''`、`fetched_at=2026-10-05 19:5x`，与第 27 项首跑时刻吻合）：
   - `daily_bars` 7 行：000001×5（含 close=8888 的指纹篡改测试行）、
     **000002/2026-09-01/close=10.0（O/H/L/V 全 NULL）**、000003×1
   - `pool_members`「测试」×3、`stock_events`「测试新闻」×1
   - mentor_lab.db 干净（用户真实档案）✓
4. 前端把 NULL 解析成 0：`C=10 ≥ O=0` → 红烛；`pmin=0` → 纵轴到 -0.28；
   烛身从缩放外灌到绘图区底 → **红竖线**。
5. 筹码分布：`turnover=None → NaN` 沿衰减累积传染全部 80 个分箱（**240 个字段 NaN**）
   → `json.dumps(allow_nan=False)` 抛 `ValueError` → **HTTP 500** →
   前端 30 秒内拿到失败 →「筹码接口无响应」。

## 教训（两条都进了长期流程）

1. **「测试全绿」必须附带「生产库没被写」的核对** —— 第 27 项首跑 26 个失败时，
   我的注意力全在转发写法上，没有意识到失败的测试正在往真实数据盘里写夹具；
   重跑全绿后也没有回头清理失败期留下的脏数据。**测试隔离失效的危害不在测试失败，
   而在它失败的方式是「写穿到生产」**。
2. **store 层要设最低入库标准**：service 层已有 `validate_bars`，但它只是
   「有的调用方会调」；凡能绕过它直达 `upsert_bars` 的路径（测试、修复工具、
   未来新调用方）都不设防。现在 store 层自带兜底校验，service 层校验保持不变。
