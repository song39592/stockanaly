   **那次跑出的 26 个失败里，夹具数据直接写进了用户的真实分片库**。
2. 随后改成 `sys.modules` 别名转发重跑全绿 —— **但坏那次写入的行没人清理**
   （重跑用的是临时目录，碰不到已落进真实库的旧行）。
3. 污染行（`source=''`、`fetched_at=2026-10-05 19:5x`，与第 27 项首跑时刻吻合）：
   - `daily_bars` 7 行：000001×5（含 close=8888 的指纹篡改测试行）、
     **000002/2026-09-01/close=10.0（O/H/L/V 全 NULL）**、000003×1

4. 前端把 NULL 解析成 0：`C=10 ≥ O=0` → 红烛；`pmin=0` → 纵轴到 -0.28；

## 教训（两条都进了长期流程）

1. **「测试全绿」必须附带「生产库没被写」的核对** —— 第 27 项首跑 26 个失败时，
   我的注意力全在转发写法上，没有意识到失败的测试正在往真实数据盘里写夹具；
   重跑全绿后也没有回头清理失败期留下的脏数据。**测试隔离失效的危害不在测试失败，
   而在它失败的方式是「写穿到生产」**。
2. **store 层要设最低入库标准**：service 层已有 `validate_bars`，但它只是
   「有的调用方会调」；凡能绕过它直达 `upsert_bars` 的路径（测试、修复工具、
   未来新调用方）都不设防。现在 store 层自带兜底校验，service 层校验保持不变。

## 续集：修 bug-04 时又挖出两层污染（同源，但**不是**测试写的）

修完夹具柱后跑策略回测，发现 `price=8888.0` —— 那是被删掉的篡改测试值。
追下去发现**污染面比第一轮清理发现的更大**，且**第一轮的扫描条件太窄漏了它们**：

### 续集 1：`adjust_factors` / `dividends` 里的夹具（致命）

| 表 | 行 | 危害 |
|---|---|---|
| `adjust_factors` | `000001 / 1900-01-01 / 1.0` | 无害但是夹具 |
| `adjust_factors` | **`000001 / 2026-06-11 / hfq_factor=2.0`** | **后复权从 2026-06-11 起价格翻倍** |
| `adjust_factors` | `000004 / 2026-06-11 / 2.0` | 同上（000004 不在池内，暂时无害） |
| `dividends` | `000004 / 2026-06-11 / 5.0` | 同上 |

全部 `source=''` + `fetched_at` 落在污染时段 → 4 行已删（`source` 空值归零）。
第一轮只扫了 `daily_bars` 的可疑行，**没扫 factors 库** —— 这是扫描范围的疏漏。

### 续集 2：000001 有 **177 行 `close=8888.0`**（上游字段错位，非测试）

- 现象：`close=8888.0`，而 `open/high/low` 全正常（如 11.5/11.68/11.48）——
  **close 单独错位**，策略回测的 `price=8888.0`、盈亏千万级都是它带的。
- 来源：腾讯证券接口在某次拉取（2026-10-05 每日自动更新时段）对这些日期返回错位的 close。
  **今天重新拉取，源返回的是正确值**（11.67 等），说明是上游的**临时**异常。
- 第一轮为什么漏：扫描条件是 `source='' OR open IS NULL OR close<=0`，
  `close=8888` 有完整 O/H/L 且为正数，**一条都不匹配**。
- 处理：全库扫「`close`/`open` 越出当日 `[low, high]` 区间」→ 定位到这 177 行
  （**只影响 000001 一只**；600519 的 1555.0 是茅台真实价格，落在区间内，不算畸形）
  → 用 `price_service.fetch_daily` 重新拉 2026 全年覆盖（181 行）→ **畸形行归零**。
  随后 `meta_set` 补记 factors.db 的 `_meta.last_write_at`（裸 sqlite3 写会绕过记账，
  导致 integrity 报「复权因子文件被外部改动」，已修正回 `ok=True`）。

### 因此把入库校验加严了一档

`_bad_bar` 新增**一致性检查**（bug-04 首版只查「缺字段 / 非正数」）：

```python
lo, hi = float(bar["low"]), float(bar["high"])
for key in ("open", "close"):
    v = float(bar[key])
    if v < lo * 0.99 or v > hi * 1.01:
        return "%s=%.4f 越出当日区间 [%.4f, %.4f]" % (key, v, lo, hi)
```

拒收行为实测（构造输入）：

| 输入 | 结果 |
|---|---|
| `close=8888` 型字段错位 | 拒收：`close=8888.0000 越出当日区间 [11.4800, 11.6800]` |
| `close` 低于 `low` | 拒收：同上格式 |
| 正常柱 | 放行 |
| 缺 O/H/L（测试夹具型） | 拒收：`缺少 open` |

**教训补一条**：清理污染时**扫描条件要按「数据的物理约束」写，不能按「我这次知道的
症状」写**。第一轮按「空值/非正」扫，漏掉了「字段错位」和「另一个库」两类；
第二轮改成「close 必须落在 [low, high] 内」才把 177 行挖出来。
