# 24 · 新增：定时清理（日志轮转、旧诊断包、过期缓存）

> 状态：待办　|　优先级：中　|　收益 ★★★☆☆ / 风险 ★★☆☆☆　|　**依赖 21 / 22 / 23**

## 问题
新增 `<data>/logs/` 与 dumplog 后会产生持续增长的产物（日志、dump zip、缓存），
没有清理策略会把数据盘慢慢撑满（对比：`bars/` 已经 2.1 GB）。

## 现状：**已有现成的调度循环，不要新建**
`download_service.py` 里已经有一套每日调度：
- `AUTO_UPDATE_HOUR = 18`（:61）、`FRESHNESS_DAYS = 10`（:62）、`SCHEDULER_INTERVAL = 60`（:63）
- `_scheduler_tick()`（:662）—— 读 `download_store` 的开关（`auto_update` / `idle_download`）
- `_scheduler_loop()`（:677）：`while True: tick(); sleep(60)`
- `_start_background()`（:946-953）：模块导入即启动 daemon 线程

清理应该**挂进这个已有的 tick**，而不是再起一个线程。

## 建议做法
1. 新建 `cleanup.py`（或 `core/cleanup.py`），提供 `run_once()` 与 `schedule_tick()`：
   - 日志：删除 `<data>/logs/` 下超过 N 天的 `backend.log.*`、`uvicorn-error.log.*`（默认 14 天）
   - 诊断包：只保留最近 N 份 `dump-*.zip`（默认 10 份）
   - 缓存：清理 `<data>/cache/` 中超过 N 天未访问的文件
   - 可选：`chip/processed/` 下超过 M 周的 `scr90_rank_*.json`（周榜按周缓存，跨周文件会一直堆积）
2. 在 `_scheduler_tick()` 里加一次调用：**每天只在某个时刻执行一次**（用「上次执行日期」去重，与现有 `_kick_auto_update` 的思路一致）。
3. 提供 `GET /api/system/cleanup`（手动触发）与保留天数配置（写在 `config.py` 或数据盘的 `config/` 里）。

## 注意（踩坑点）
1. **绝不能碰 `bars/`**（2.1 GB 行情分片）—— 那是业务数据，不是缓存。清理白名单要显式排除 `bars/`、`state/`、`config/`。
2. `instance.lock` 在 `state/`，不要被当成「过期锁文件」清掉 —— 它由 `instance_lock` 模块管理。
3. 清理要**先记录再删**（写日志：删了什么、多少字节），便于追溯。
4. 调度去重必须按**日期**而非「每 tick」，否则 60 秒一轮会疯狂扫描目录。
5. 周榜缓存（`scr90_rank_*.json`）删除前确认：第 21 项把用户配置放 `config/`，结果文件仍在 `chip/processed/`；
   清理跨周文件时要保证**当前周那份**不动（判据：文件名里的周一 != 当前周节点）。

## 验收

- [ ] 连续运行 2 天以上，确认**每天只清理一次**（不是每 60 秒）
- [ ] `bars/` / `state/` / `config/` 未被触碰
- [ ] 当前周的 `scr90_rank_<本周>.json` 不会被删
- [ ] 后端启动无异常；`/health` 正常
