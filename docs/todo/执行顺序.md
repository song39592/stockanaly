# 推荐执行顺序 + 独立性矩阵

> **收尾约定（每次改完必做）**：完成一项后 ——
> ① 该项文件的「状态」改成「已完成」并回填实际改动；
> ② **同步更新本文件**（独立性矩阵 + 阶段表都打上 ✅已完成）；
> ③ 提交一次（生成物如 `股票池追踪系统.exe` 一并提交）。

> **修订（按你的意见）**：结构先行。
> 理由不只是「整理位置更重要」，还有一个实际原因：**部分去重项会新建文件**
> （01→`Palette.cs`、02→`J.cs`、06→`Cards.cs`、09→`jsonutil.py`、10→`chip_formulas/core/scr.py`）。
> 若目录结构没先定好，这些新文件会先落在旧位置、之后还要再搬一次。
> 所以原则变成：**「结构先到位，去重项排在『它的目标位置已建立』之后」**。

**结论**：**绝大多数项都能单独执行 + 单独验证**。
只有三组是真正的链：
1. `21 → 22 → 23 → 24`（日志与清理链，缺一就没有可验证的产物）
2. `34 → 10`（chip 搬完，`scr.py` 才能落在最终位置）
3. `35` 必须最后（它改的根目录是所有人引用的起点）。

> **关于 `bug-NN` 编号**：缺陷用独立前缀，**不占用 00~35 的数字编号**。
> 原因：`35` 标注了「必须最后或不做」，新数字项要么插在它前面（编号与顺序倒挂、
> 让人以为没做完），要么排在它后面（直接违反「必须最后」）。用前缀既保住了 00~35
> 的排序语义，也让缺陷在索引里一眼可辨。缺陷不排进阶段，只在阶段表里单点标注插入位置。

`27 → 28~34` 之间**不是硬依赖** —— 用「旧路径留兼容转发」的做法，任何一个 feature 都能单独搬、单独验证；
把它们排序只是为了**先在低风险的 core 上验证转发模式可行**。

## 三、每批源码搬家的固定动作（27~34 通用）
1. 建目标子包目录（带 `__init__.py`）。
2. `git mv` 模块进去（**不要用普通移动**，否则丢历史）。
3. 在新位置修正 import（相对导入 / 用 `core.xxx`）。
4. **在旧路径留兼容转发** —— 让还没迁的模块继续可用。
   ⚠️ `from x import *` **不会导出下划线开头的名字**（如 `_ak`、`_json_safe`），必须显式补充列出。
5. 启动后端，看 `/health` 的 `_module_errors` 是否为空。
6. 跑一遍相关页面/接口。
7. **确认没有其它模块再 import 旧路径后**，才删掉兼容转发。
