# 11 · 后端：路由错误体形状统一（只统一形状，不动 HTTP 状态码）

> 状态：**已完成**（2026-10-06）　|　优先级：高　|　收益 ★★★★☆ / 风险 ★★☆☆☆
> 统一后的形状：`{"ok": false, "detail": "…", "error": {"code": "…", "message": "…"}}`

## 实际落地（与原建议的差异，逐条说明）

1. **落地为 `backend_fastapi/apiutil.py`**（原建议就是这个名字），提供
   `ok()` / `fail()` / `soft_fail()` / `guard()` / `http_error()` / `install(app)` /
   `code_of()`。
2. ⭐ **主力杠杆是 `install(app)` 挂全局异常处理器**，而不是逐个路由改 —— 全仓
   **90 余处** `raise HTTPException(detail=…)` **一行未改**即拿到统一形状。
   原文档只列了 4~5 个路由文件，实际 `HTTPException` 遍布
   features/{stock,system,download,history,mentor} 全部路由，逐个改不现实。
3. ⭐ **`detail` 字段**必须保留（不是冗余）：前端有 8 处直接读 `detail` 取提示文案
   （下载页 3、系统页 2、个股页 2、估值页 1），它们走的都是 `HTTPException`。
   保留它是**向后兼容锚点**；前端新取值入口是新增的 `J.ErrMsg()`。
4. ⭐ **必须注册 `starlette.exceptions.HTTPException` 而不是 `fastapi.HTTPException`**：
   路由不存在的 404 / 方法不对的 405 抛的是 starlette 那个（fastapi 的是它的子类）。
   只注册 fastapi 的，404 会漏出去仍是裸 `{"detail":"Not Found"}`，等于又多一种形状。
   422 校验错误一并接管（原本是 `{"detail":[{loc,msg,type},…]}`，数组）。
5. ⭐ **踩坑（真实踩到并修掉）：`raise apiutil.fail(...)` 是错的** ——
   `fail()` 返回 `JSONResponse`，**不是 Exception**，raise 它会让 FastAPI 落到兜底
   处理器，回 `500 Internal Server Error`（连错误体都没有，比改之前更糟）。
   正确写法是 `return apiutil.fail(...)`；另提供 `http_error()` 给想 `raise` 的地方。
   `dist_routes` 的 4 处已全部改为 `return`。
6. **`indicators_routes._err` / `_CODE_ERR` 并入 apiutil**（`_err = apiutil.fail` 别名，
   注意**参数顺序反过来了**：`(message, code, status)`，4 处调用点同步改）。
   `strategies_routes` 的 3 处逐 handler try/except 被 `guard()` 装饰器消除。
   ⚠️ `guard` 的 `code` 参数支持 str / dict / None 三态，dict 用于保住本域更具体的码
   （`KeyError → UNKNOWN_STRATEGY` 而不是通用 `UNKNOWN_KEY`）—— 直接用默认会降级。
7. **状态码按踩坑点 3 保持不变**（二分法：状态码=请求是否合法，ok=业务是否成功）。
   `chip/rank` 仍是恒 200 + ok=false（前端轮询依赖），走 `soft_fail()` 而非 `fail()`。
   `rank_service` 5 处字符串 error 改为结构化（`NOT_COMPUTED` / `CACHE_CORRUPT` /
   `WRITE_FAILED`），**周榜仍是 200**。`dist_routes` 业务失败保留外层 `code`
   （那是**股票代码**，不是错误码，别覆盖）。
8. ⭐ **前端必须同步适配**（原文档踩坑点 4 说了要，但低估了范围）：新增
   `J.ErrMsg()` 兼容三种形状（error 是对象 / error 是字符串 / 只有 detail），
   替换 9 处调用点（StockPage 5、MarketPage 1、ValuationPage 1、Http.cs 1、ChipRankPage 1）。
   ⚠️ 关键陷阱：`J.Str()` 拿到 Dictionary 会 `Convert.ToString` 成
   **类型名垃圾串**（"System.Collections…"），所以**必须先判类型再取值**；
   `ChipRankPage` 那处改前读的是字符串 error，改后是对象，不改就会显示垃圾。
9. **`csc` 编译 exit 0**，exe 已重新编译（244736 字节）。

## 问题
4 套路由各有自己的错误风格，前端要为 4 种风格写 4 套解析。
而 `indicators_routes.py` **已有一个现成的封装种子**，`strategies_routes.py` 有一份等价的字典 —— 两份是同一设计。

## 证据

| 文件 | 风格 |
|---|---|
| `chip_routes.py` | `HTTPException` 400/500，**没有** ok=false 路径（:47,49,64,73,87） |
| `chip_dist_routes.py` | 混合：参数错误抛 400/500（:53,57,63,65,71,75），业务性失败返回 `200 + ok=false`（:73） |
| `chip_rank_routes.py` | **恒 200 + ok 字段**，从不抛（:26,38,49,71） |
| `strategies_routes.py` | `JSONResponse(status_code=400)` + 结构化错误码 `_CODE_ERR = {KeyError:"UNKNOWN_STRATEGY", ValueError:"BAD_PARAM", RuntimeError:"NO_DATA"}`（:67-71），逐 handler 重复 try/except（:85-88、:105-108、:120-122） |
| `indicators_routes.py` | **已有私有封装 `_err(err_code, msg, status)` + `_CODE_ERR[type(exc)] -> (err_code, status)`**（:42-43, :46-50）← 最接近公共层的一份 |

参数校验写法也不统一：`Query(min_length/max_length)` / `Query(ge,le,description)`（**默认值直接引用 service 常量，好做法**）/
Pydantic BaseModel + 手动 strip / service 层用 `re.fullmatch(r"\d{6}")` 校验（下沉了，见 `valuation_service.py:325,347`）。

## 建议做法
抽 `backend_fastapi/apiutil.py`：
```python
def ok(payload, **extra) -> dict                       # {"ok": True, **payload}
def fail(message, code="BAD_PARAM", status=400) -> JSONResponse
def guard(exc_types, handler)                          # 装饰器，消掉逐 handler 的 try/except
```
把 `indicators_routes._err`（:43）提成公共层，`strategies_routes` 与 `chip_dist_routes` 接入。

错误体统一为：`{"ok": false, "error": {"code": "...", "message": "..."}}`

## 注意（踩坑点）—— 这决定了风险高低
1. **`chip_rank_routes` 的恒 200 是刻意设计**（该模块文档第 9 行：「未算过返回 ok=false」，
   前端据此提示「先点刷新本周」）。压平成 400/500 会**打断前端轮询**。
2. `chip_dist_routes.py:73` 的 `200 + ok=false` 表示「行情不足」这类**可恢复状态**；
   `chip_routes.py:49/64/73` 的 400 表示**请求非法**。两者语义确实不同，**不该一律压平成 200**。
3. → 因此本项**只统一错误体的 JSON 形状**，保留：
   **HTTP 状态码 = 请求是否合法／ok 字段 = 业务是否成功** 这个二分。状态码统一留给后续单独评估。
4. 分阶段迁移最稳：先让新接口**同时输出** `error`（旧字符串字段）和 `error.code/message`（新结构），
   前端迁完再删旧字段，保证向后兼容。
