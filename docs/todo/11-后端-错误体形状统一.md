# 11 · 后端：路由错误体形状统一（只统一形状，不动 HTTP 状态码）

> 状态：待办　|　优先级：高　|　收益 ★★★★☆ / 风险 ★★☆☆☆（按下面做法可压到低）

## 问题
4 套路由各有自己的错误风格，前端要为 4 种风格写 4 套解析。
而 `indicators_routes.py` **已有一个现成的封装种子**，`strategies_routes.py` 有一份等价的字典 —— 两份是同一设计。

## 证据

| 文件 | 风格 |
|---|---|
| `chip_routes.py` | `HTTPException` 400/500，**没有** ok=false 路径（:47,49,64,73,87） |
| `chip_dist_routes.py` | 混合：参数错误抛 400/500（:53,57,63,65,71,75），业务性失败返回 `200 + ok=false`（:73） |
| `chip_rank_routes.py` | **恒 200 + ok 字段**，从不抛（:26,38,49,71） |
| `strategies_routes.py` | `JSONResponse(status_code=400)` + 结构化错误码 `_CODE_ERR = {KeyError:"UNKNOWN_STRATEGY", ValueError:"BAD_PARAM", RuntimeError:"NO_DATA"}`（:67-71），逐 handler 重复 try/except（:85-88、:105-108、:120-122） |
| `indicators_routes.py` | **已有私有封装 `_err(err_code, msg, status)` + `_CODE_ERR[type(exc)] -> (err_code, status)`**（:42-43, :46-50）← 最接近公共层的一份 |

参数校验写法也不统一：`Query(min_length/max_length)` / `Query(ge,le,description)`（**默认值直接引用 service 常量，好做法**）/
Pydantic BaseModel + 手动 strip / service 层用 `re.fullmatch(r"\d{6}")` 校验（下沉了，见 `valuation_service.py:325,347`）。

## 建议做法
抽 `backend_fastapi/apiutil.py`：
```python
def ok(payload, **extra) -> dict                       # {"ok": True, **payload}
def fail(message, code="BAD_PARAM", status=400) -> JSONResponse
def guard(exc_types, handler)                          # 装饰器，消掉逐 handler 的 try/except
```
把 `indicators_routes._err`（:43）提成公共层，`strategies_routes` 与 `chip_dist_routes` 接入。

错误体统一为：`{"ok": false, "error": {"code": "...", "message": "..."}}`

## 注意（踩坑点）—— 这决定了风险高低
1. **`chip_rank_routes` 的恒 200 是刻意设计**（该模块文档第 9 行：「未算过返回 ok=false」，
   前端据此提示「先点刷新本周」）。压平成 400/500 会**打断前端轮询**。
2. `chip_dist_routes.py:73` 的 `200 + ok=false` 表示「行情不足」这类**可恢复状态**；
   `chip_routes.py:49/64/73` 的 400 表示**请求非法**。两者语义确实不同，**不该一律压平成 200**。
3. → 因此本项**只统一错误体的 JSON 形状**，保留：
   **HTTP 状态码 = 请求是否合法／ok 字段 = 业务是否成功** 这个二分。状态码统一留给后续单独评估。
4. 分阶段迁移最稳：先让新接口**同时输出** `error`（旧字符串字段）和 `error.code/message`（新结构），
   前端迁完再删旧字段，保证向后兼容。
