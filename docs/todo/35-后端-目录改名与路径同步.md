## 评估结论：不做目录改名

待办原文已预先授权「评估后觉得收益不抵风险，可以不做本项」。实测后确认不抵。
**关键数据**（评估当时实测）：

| 引用面 | 规模 |
|---|---|
| 代码 / 脚本 | **44 处 / 19 个文件**（比原文预估的「11 项」更广） |
| 文档 | **113 处 / 29 个文件**（`README` + `docs/`） |
| venv | **9668 文件 / 230MB**，`pyvenv.cfg` 硬编码绝对路径，`Scripts\` 下 17 个 exe |

四条理由（按重要性）：

1. **验收标准本身无法安全执行。** 原文要求「删除 `.venv` 后跑安装脚本 → 后端能启动
   （从零验证）」。这要删掉用户 230MB / 9668 文件的 venv 并重装 akshare、pandas 等；
   一旦网络或某个包装不上，**用户系统直接不可用**。而这套系统当时正在被使用。
2. **「venv 不动」这个折中方案本身是有害的**（原文踩坑点 2 的建议）。若源码搬到
   `backend/` 而 venv 留在 `backend_fastapi/`，结果是 **venv 与源码分属两个目录** ——
   比现在更糟：探测逻辑要同时试两个位置（`StockPoolLauncher.cs:1384-1385`）、
   安装脚本跨目录、用户在 `backend_fastapi/` 里只看到 venv 看不到源码。
   等于说「必须整体迁移 9668 文件」，没有低成本版本。
3. **旧 exe 会直接失效，且替换时可能被占用。** 启动器用
   `Path.Combine(_root, "backend_fastapi", ...)` 拼了 16 处路径，桌面上的 exe 是
   **已编译产物**；改名后必须重编，而用户若正运行旧 exe，覆盖会失败。
   这不是理论风险 —— 评估时后端进程正在运行。
4. **改名不解决真问题。** 收益是「目录名不说谎」，但若将来真换框架，157 处引用
   那时照样要改 —— 改名只是**把成本提前支付**，并不降低未来成本。
   真正的结构收益在第 27~34 项的「按功能分层」，那部分**已经拿到了**
   （`features/` 分层 + 公共件收敛 + 顶层转发兼容层）。

补充：157 处引用里有 **113 处在文档**，而文档路径引用**不产生运行时风险**；
真正必须同步的只有 44 处代码/脚本。

## 已交付的部分（本次实际改动）

虽然不改名，但把**将来改名时最容易漏、且漏了会误导用户**的那一处修掉了：

`core/config.py` 的三处**用户可见提示文案**原本硬编码 `backend_fastapi/.env`
（原文验收第 4 条「LLM 未配置时的提示文案不再出现旧目录名」）。现改为
`_ENV_HINT = f"{PROG_DIR.name}/.env"` 动态派生。

为什么单独值得做：漏改这三处的后果不是编译失败，而是**提示用户去一个
不存在的路径填密钥** —— 用户会照做，然后 LLM 依然不通，且很难归因。
现在改名只需移动目录，文案自动跟随。

实测：`_ENV_HINT` 派生正确；`llm_config_problem()` 三条文案
（缺密钥 / 占位符 / 密封但解不开）格式正确、无未替换占位符、目录名动态；
57 个单元测试全绿。

## 注意（踩坑点）
1. **`.env` 是用户已存在的文件**：改名后若迁移不到位，用户会突然「LLM 未配置」。
   必须做**自动迁移**：新目录没有 `.env` 但旧目录有 → 复制过去（或提示）。
2. **venv 是 3953 个文件的目录**：一起改名意味着路径变更，已安装包里的**绝对路径脚本**（如 `Scripts/*.exe`）
   可能失效 —— 风险很高。**建议 venv 不动**，只改源码目录名并让探测逻辑兼容两个位置。
3. 启动器 exe 需要重新编译，且**用户可能正在运行旧 exe**（改名后旧 exe 找不到后端目录会直接报错）。
4. `README` 与 `docs/` 里的路径引用要全文检索替换（`backend_fastapi` 出现次数很多）。
