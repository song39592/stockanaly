# 18 · 前端：异步加载骨架（Task.Run + Invoke）20+ 处 —— **留到最后做**

> 状态：待办　|　优先级：低（**但收益大**）　|　收益 ★★★☆☆ / 风险 ★★★★☆
> ⚠️ 本项风险最高：每个调用点的**竞态守卫都不一样**，抽不好会引入交叉刷新（A 请求的结果盖到 B 上）。

## 问题
`Task.Run(delegate { try { 请求 → Invoke(渲染) } catch { Invoke(失败) } })` 这套骨架在前端出现 **20+ 次**，
但每处的竞态守卫各不相同，不能直接套一个通用 `RunAsync`。

## 证据

### 同构的加载方法（StockPage 至少有 8 个）
`StockLoadName:670` / `StockLoadHistory:705` / `StockLoadBoards:926` / `StockLoadChip:1239` /
`StockLoadBasic:1049` / `StockLoadSaolei:1706` / `StockLoadValuation:1911` / `StockLoadAi:2004`
另：ValuationPage 2 处、ChipRankPage 4 处、StrategyPage 4 处、MarketPage 若干。

### 三类不同的竞态守卫（这就是风险所在）
| 守卫方式 | 位置 |
|---|---|
| 「round 是否仍是当前轮」`if (round != _stockRound) return;` | StockPage:707, 720, 726（个股切换时作废旧请求） |
| 「code 是否还是当前」`if (_stockCode.Text.Trim() != code) return;` | StockPage:680（名称查询） |
| 「busy 标志」`if (_scrBusy) return; _scrBusy = true; ... Invoke{ _scrBusy = false; ... }` | ChipRankPage 4 个方法逐字重复 |

### 相关：「加载中」文案 18 处散落
StockPage.cs:190("待加载"), 383, 654, 815, 816, 1053, 1243, 1913；
ValuationPage.cs:322,324；StrategyPage.cs:635；MarketPage.cs:499；DownloadPage.cs:175；ChipRankPage.cs:193。

## 建议做法
**不要**先抽通用 `RunAsync`。建议：
1. 先抽一个**只负责线程的薄封装**，把「守卫」作为回调留在调用侧：
   ```csharp
   private void RunAsync(Action load, Action<Dictionary<string,object>> onOk, Action<string> onFail, Func<bool> stillValid)
   ```
   —— `stillValid` 由每个调用点自己提供（round 比对 / code 比对 / 都不是就返回 true）。
2. 真正的大重构留到「准备系统性重写 StockPage 那 8 个 Load 方法」时一起做。

## 注意（踩坑点）
1. **守卫不能统一**：抽成无守卫的通用方法 → 快速切换股票时会出现**交叉刷新**（旧请求后返回，把新股票的数据盖掉）。
   这是本项唯一但致命的风险。
2. `_scrBusy` 这类「忙标志」在失败路径也要复位 —— 现在 ChipRankPage 是 `Invoke` 里 `finally` 语义复位的，
   抽公共方法时别漏掉异常路径的复位，否则按钮点一次之后永久卡死。
3. 轮询（`ChipRankPage._scrTimer`）与单次请求是两回事，别一起抽。
4. 「加载中」文案统一要小心：有些是**首屏占位**（"待加载"），有些是**重试中**，语义不同。
