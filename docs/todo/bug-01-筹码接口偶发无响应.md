# bug-01 · 筹码分布偶发「筹码接口无响应」（超过 30s 被启动器判死）

> 状态：**已完成**（2026-10-05）　|　类型：**偶发**（上游数据源卡顿时才出现，重开即不复现）
> 优先级：高　|　收益 ★★★★☆ / 风险 ★☆☆☆☆

## 现象

个股页 K 线正常绘制，但筹码分布区域显示红字 **「筹码接口无响应」**（`launcher/StockPage.cs:1151`）。
**关掉重开或再次打开该股就正常了**，后端日志里也**没有任何错误**。

## 根因

红字的触发条件只有一个（`StockPage.cs:1147`）：

    if (!GetText(url, 30000, out body) || string.IsNullOrEmpty(body))   // ← 启动器只等 30 秒

顺着这条链往里看，`/api/chip/dist` 的**冷路径**上藏着一个没有上限的串行重试：

    chip_dist 路由 → chip_formulas.compute
      → data.load_input(..., offline=False)
        → _lockup_of(code)                      # 锁仓修正
          → stock_profile.lockup_ratio(code, 5.0)
            → free_top_holders(code)
              for period in _report_periods():               # ← 8 个报告期
                  _ak(ak.stock_gdfx_free_top_10_em, ..., timeout=20)   # ← 每个最多 20s
                  if df is None or df.empty: continue          # ← 空结果也继续试下一期

- `_report_periods()` 默认返回 **8 个**报告期（季报 / 年报截止日，由近及远）；
- 每个 `_ak(..., timeout=20)` 由看门狗线程**硬切断**，即最多阻塞 20s；
- 两者**串行累加 → 最坏 8 × 20 = 160 秒**；
- 而启动器只等 **30 秒**。

平时**第一个报告期就命中**（实测 0.4~0.9s），所以绝大多数时候看不出问题。
只有当东财股东接口**变慢或返回空**时才会逐期往后试，耗时迅速堆过 30s → 启动器放弃 → 报「无响应」；
后端其实还在跑完，并把结果写进 `stock_profile._CACHE`（TTL 6 小时）——
**这就是「再次打开不复现」的原因**。

> 讽刺的是 `lockup_ratio` 的注释已经写了设计意图：
> 「**失败一律回退 (0.0, 1.0)**：股东数据是外部网络取数，任何异常都不该拖垮筹码主流程」。
> 但它只防住了「**失败**」，没防住「**变慢**」——上游卡住时不抛异常、不返回 None，
> 只是每次都慢 20 秒，于是这个保护形同虚设。

## 同一形态的第二个受害者

`stock_profile.top_holders`（十大股东，供个股「基本信息」页 `/api/stock/profile`）
是**完全相同的 8 期 × 20s 串行结构**，同样没有预算。一并修掉。

## 修法

新增 `_walk_report_periods(fetch, budget)`，给「往回试报告期」加**总时间预算**：

- `_HOLDERS_BUDGET = 6.0` 秒（实测首个报告期 0.4~0.9s，6s 已留 7 倍余量）；
- 每期实际超时取 `min(20, 剩余预算)`；
- 预算用尽立即停，**哪怕后面的报告期其实有数据** —— 取不到就按既有约定回退
  （筹码页不做锁仓修正，系数 1.0；股东列表为空并给出 `error`）。
  上游不稳时不该让用户等一分钟。

两个函数都改为调用它，行为在「上游正常」时**完全不变**。

## 踩坑（验证时自己踩的，值得记）

第一次验证时我把「数据源卡死」模拟成「无视 timeout 睡死 20s」，结果预算没生效（仍 20s）。
原因是**真实 `_ak` 是按传入 timeout 硬切断的**，我的假实现没有模拟这一点 ——
等于测了个不存在的行为。改成「按传入 timeout 睡满」后才忠实还原，预算随即生效。
**教训：验证用的 mock 必须对齐真实实现的语义，否则测的是自己想当然的版本。**

## 顺带发现，未修（供后续判断）

1. **`/api/stock/profile` 冷启动 16.4s**（热 0.1s）。慢在 `company_info` 的**双源串行回退**
   （巨潮 `timeout=20` → 同花顺 `timeout=20`，最坏 40s）。它在启动器的
   **90s** 超时之内（`VRequest` 默认 `timeoutMs = 90000`），**不会**报「无响应」，
   故本次不动。若以后想加快冷启动，这里是下一个目标。
2. **`000001` 等个股报「数据指纹校验未通过（内容指纹不一致）」**，
   `/api/chip/dist?code=000001` 返回 `ok=false`。这是**独立问题**
   （`repair_apply.log` 曾在 10/03 重算 8298 条指纹），与本次超时无关，未处理。
3. `chip_dist` 路由调的是 `chip_formulas.compute(...)`，**绕过了**
   `indicators/data.py` 里 `_chip_frames` 的 `lru_cache` —— 指标侧有缓存、
   交互侧每次全量重算。滚轮缩放会反复触发（`ScheduleChipReload` 虽有 400ms 防抖）。
   本次未改（会改变缓存行为，需单独评估内存占用），但值得后续统一。
