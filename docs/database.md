# 数据库结构

> 所有运行期数据集中存放在**数据根目录**下，默认是「程序上一级的 `stockanaly-data`」
> （与仓库并列），可用 `.env` 的 `DATA_DIR` 或环境变量 `STOCK_DATA_DIR` 指定。
> 位置与迁移逻辑见 `backend_fastapi/storage.py`，表结构定义见 `price_store.py` / `history_store.py` / `mentor_store.py`。

**三个存储库的分工**

| 库 | 特点 | 内容 |

## 二、主库 `stock_history.db`

股票池与消息面。仅 5 张表，体积通常在几百 KB。

```text
   pool_snapshots ──── 1:N ──── pool_members
   （每个交易日一条）            （该日池内每只股票一条）
        │
        │ snapshot_date
        ▼
   sync_jobs ────────────────────（记录该日期的后台同步任务）
                                  通过 snapshot_date 逻辑关联，未建外键

   stock_events ──────────────────（按 code 归属个股，独立于池快照）
        │
        ▼
   event_sync_state ──────────────（每只股票的最后抓取时间，用于 12h 缓存判断）
```

| 表 | 主键 | 行数量级 | 说明 |
|---|---|---|---|
| `pool_snapshots` | `snapshot_date` | 每交易日 1 行 | 每日池快照：日期、只数、导入时间 |
| `pool_members` | `snapshot_date` + `code` | 每次导入 × 只数 | 入池明细：名称、行业、地区、**导入价**、**导入日涨跌幅** |
| `stock_events` | `id`（内容哈希） | 每股几十~几百行 | 公告与新闻：标题、日期、来源、链接、摘要 |
| `event_sync_state` | `code` | 每股 1 行 | 消息面最后抓取时间（12 小时 TTL 依据） |
| `sync_jobs` | `id` | 每次任务 1 行 | 后台同步进度：总数、完成、失败、错误摘要 |

**字段要点**

- `pool_members.import_price` / `import_change`：**只有服务端有这份原始值**。
  前端 `localStorage` 只存 `{code, name, industry, region}`，所以这两个字段丢了不可再生。
- `stock_events.id` 由 `code + kind + title + published_at + url` 做 SHA-256 取前 32 位，
  天然去重，重复抓取不会产生重复行。

## 三、行情库 `bars/`

### 3.1 按年分片的日 K：`bars_YYYY.db`

```text
   bars_2024.db   daily_bars   2024 年的原始价
   bars_2025.db   daily_bars   2025 年的原始价
   bars_2026.db   daily_bars   2026 年的原始价
        │
        │  年份取自 trade_date 前四位，写入时自动路由
        │  查询跨年时按年份逐库读取后合并排序
        ▼
   同一张表结构，分布在不同文件里
```

| 字段 | 类型 | 说明 |
|---|---|---|
| `code` | TEXT PK | 6 位股票代码 |
| `trade_date` | TEXT PK | `YYYY-MM-DD` |
| `adjust` | TEXT PK | **固定为 `raw`**（不复权原始价），保留此列只为结构兼容 |
| `open/high/low/close` | REAL | 原始价（**不是复权价**） |
| `volume` / `amount` | REAL | 成交量 / 成交额 |
| `turnover` | REAL | 换手率 |
| `amplitude` / `change_pct` / `change_amount` | REAL | 振幅 / 涨跌幅 / 涨跌额——**腾讯源不提供，故常为空**，可用 OHLC 现算 |
| `source` | TEXT | 数据来源（东方财富 / 腾讯证券），便于排查**混源偏差** |
| `fetched_at` | TEXT | 抓取时间 |

- 主键 `(code, trade_date, adjust)`，且建表使用 **`WITHOUT ROWID`**——
  主键即聚簇数据，省掉一份 rowid 索引，约省 20~30% 空间且读取更快。
- **单年约 250 MB**（5000 只 × 242 个交易日），**单文件小、便于备份与归档**，老年份可设为只读。

### 3.2 复权参考数据：`bars/factors.db`

| 表 | 主键 | 说明 |
|---|---|---|
| `adjust_factors` | `code` + `ex_date` | **后复权因子 `hfq_factor`**：以上市首日为基准（值为 1.0），**单调递增、历史不变** |
| `dividends` | `code` + `ex_date` | 除权除息明细：公告日、股权登记日、每 10 股送股/转增/派息、实施进度 |

**为什么只存 `hfq_factor`、不存 `qfq_factor`**

| | `hfq_factor` | `qfq_factor` |
|---|---|---|
| 基准 | 上市首日 | **最新交易日** |
| 历史值是否变化 | **永不变** | **每天都在变**（每次除权全序列重写） |
| 是否适合入库 | ✅ | ❌ 等于把「会变的数据」请回来 |

两者互为常数倍，任取其一即可换算，所以只留稳定的那个。

### 3.3 复权价一律现算

```text
hfq(t)        = raw(t) × hfq_factor(t)
qfq(t, as_of) = raw(t) × hfq_factor(t) ÷ hfq_factor(as_of)
```

- `as_of` 是**复权基准日**，缺省为区间内最后一个交易日（等价于数据源的常规前复权）。
- **回测必须传回测起点**作为基准：这样历史价格不含未来信息，且同一段历史每次回测结果一致。
- 库里只存一份原始价，比存三套复权价**节省约 2/3 空间**（5000 只 × 10 年：2.5 GB vs 7.4 GB）。

## 四、实验室库 `mentor_lab.db`

独立业务闭环，6 张表。所有 `*_json` 字段存的是序列化后的结构化数据。

```text
   mentors ─┬─ materials ──── extractions
            │   （上传的资料）    （模型提炼结果，待人工复核）
            ├─ daily_views
            │   （每日观点，待人工复核）
            └─ skill_versions ──── evaluations
                （规则版本，active/archived）  （回测评估，人工决策）
```

| 表 | 说明 |
|---|---|
| `mentors` | 导师档案 |
| `materials` | 上传的 PDF / 文本：原文、分段、`sha256`（同导师内去重）、解析状态 |
| `extractions` | 模型从材料中提炼的结构化内容 + 原始输出，供人工复核 |
| `daily_views` | 每日观点及其 `data_as_of` |
| `skill_versions` | 规则版本（含 `parent_version` 与状态流转），可追溯的迭代链 |
| `evaluations` | 某版本的评估结果 + 人工决策（`pending` / 通过 / 驳回） |

## 五、文件型数据 `chip/`

筹码体系 · SCR 选股的数据，以**原文件**形式保留（不经数据库）：
导入的是行情软件导出的制表符文本，保留原件便于追溯与重新解析。

```text
   chip/
   ├── raw/         导入的原始文件，保持原文件名
   │                （文件名的 8 位日期自动解析为默认日期，可在页面手改）
   ├── processed/   最近一次计算的三档分类结果
   │                scr_result_YYYYMMDD.json（明细）
   │                scr_summary_YYYYMMDD.csv （汇总）
   └── meta.json    文件 → 日期映射；记录被手动修改过的日期
```

## 六、容量规划

按实测单条日 K 含索引约 **203 字节**推算：

| 规模 | 行数 | 体积 |
|---|---|---|
| 5000 只 × 1 年 | 121 万 | 约 250 MB |
| 5000 只 × 5 年 | 605 万 | 约 1.2 GB |
| **5000 只 × 10 年** | **1210 万** | **约 2.5 GB** |

按年分片后每年一个约 250 MB 的文件，可单独备份 / 归档，**扩展时只是多出几个年份文件，不需要改代码**。

## 七、设计约定

1. **数据与代码分离**——数据目录在项目外，删项目、重 clone、`git clean` 都不影响数据。
2. **只存事实，派生现算**——库里只有原始价，复权价、涨跌幅、振幅等都按需计算。
   这条原则让"三口径"这类冗余从 7.4 GB 压到 2.5 GB。
3. **历史稳定的数据才入库**——`hfq_factor` 入、`qfq_factor` 不入，理由同上。
4. **只复制、不删除**——迁移与清理都带安全校验（目标为空时拒绝执行），
   源数据在确认无误前一律保留。
5. **单来源失败只降级**——任一数据源异常不影响其他模块，原因写入响应的 `errors`。
6. **跨库不建外键**——不同库之间（如行情与池快照）通过 `code` 逻辑关联，
   由应用层保证一致性，避免 SQLite 跨库约束带来的耦合。
7. **格式版本化 + 防篡改**——每个库的 `_meta` 记录 `schema_version` 与
   `last_write_at` 并做 HMAC 签名，可发现外部直接改库（详见第八节）。

## 八、数据可信：原则与防篡改

**目标**：发现有人绕过程序、直接用数据库工具改数据（例如手改历史 K 线、篡改池快照），
并在发现之后按既定原则处理。

### 8.0 可信原则（本项目的第一原则）

> **丢数据可重拉，错误数据不可接受；可用性可以让步，正确性不能让步。**

由此派生四条：

| 原则 | 含义 |
|---|---|
| **① 不展示可疑数据** | 校验不通过就拒绝返回（`UntrustedDataError`），宁可该股暂时无图，也不把可能已被篡改的内容交给上层计算 |
| **② 不静默丢弃数据** | 修复一律用**数据源真值整体替换**；**先抓取、后写入**，失败则抛错并**保留库中原有数据** |
| **③ 可信优先于完整** | 二者冲突时宁可整体重拉，也不保留来源存疑的数据（见 8.6 取舍） |
| **④ 其余库只报告** | 除日 K 的自动替换外，其余库检测到异常只写入 `issues`，是否重建由使用者决定 |

**防护是分层的，且能力并不对等**——务必按下表理解，不要以为「所有数据都有同等级保护」：

| 数据 | 内容指纹 | 被改动后 |
|---|---|---|
| **日 K**（`daily_bars`） | ✅ 按股 HMAC，覆盖**全部行情字段** | 读取即拒绝 → 自动全量重抓替换，**能定位到具体哪只股票** |
| **池快照 / 消息面 / 复权因子 / 除权** | ❌ 只有 `_meta` 结构级 | 只能给出「整库被外部写过」的模糊信号，**300 秒容差内无感**，且**定位不到具体记录** |

> ⚠️ **最大的遗留风险**：`pool_members.import_price` 是**唯一不可再生**的数据
> （数据源没有「那天的选股结果」），而它恰好属于「无内容指纹」的那一类——
> 一旦被改，**既发现不了、也补不回来**。

### 8.1 机制：元信息 + HMAC 签名

每个库都有一张 `_meta` 表，记录关键元信息，并对**内容本身**做 HMAC 签名：

```sql
CREATE TABLE _meta (
  key        TEXT PRIMARY KEY,   -- schema_version / last_write_at
  value      TEXT NOT NULL,
  updated_at TEXT NOT NULL,
  hmac       TEXT NOT NULL       -- sign(key | value | updated_at)
) WITHOUT ROWID;
```

| 元信息键 | 含义 |
|---|---|
| `schema_version` | **入库格式版本**，代码里递增；启动时比对，不一致提示需迁移 |
| `last_write_at` | **程序最后一次写入该库的时间** |

**签名密钥**：首次运行时自动生成 256 位随机密钥并写入 `backend_fastapi/.env`
（该文件不进版本库）。可用 `DATA_SECRET` 环境变量覆盖。

**零侵入的写入记录**：更新发生在 `db.connect()` 的事务提交出口——
任何写事务（`total_changes > 0`）提交前自动刷新元信息，**各 store 无需关心**。

### 8.2 三层检查（`integrity.check_library`）

| 检查 | 能发现什么 |
|---|---|
| **签名有效性** | 手改了 `_meta` 的值却没同步改签名 |
| **写入时间吻合** | 库文件（含 `-wal`，**刻意不含 `-shm`）的 mtime 明显晚于 `last_write_at`，说明存在**程序之外**的写入 |
| **结构版本 + 期望表** | 格式版本不符、表被删除等结构性破坏 |

容差 **300 秒**——程序自己的写入与记录时间天然一致，因此**不会误报**。

⚠️ **计时必须早于打开库**（曾因此必然误报）：打开 WAL 库（哪怕纯读查询）会创建 `-wal`，
其 mtime 就是「此刻」。若在 `sqlite3.connect` 之后再取时间，就会把「打开库」当成
「被外部写入」，导致只要库有年龄就稳定报「相差 N 分钟」。现已在 `check_library` 中
把取时间提前到连接之前。`-shm` 同理被排除——它是共享内存索引，任何一次打开都会更新它。

### 8.3 实测检出效果

```text
场景 1  直接改数据并把文件时间推后
        status: tampered
         ⚠ 文件修改时间明显晚于程序记录（相差 120 分钟），疑似被外部工具改动

场景 2  只改 _meta 的记录值，不同步改签名
        status: tampered
         ⚠ 元信息「last_write_at」签名不匹配，疑似被直接修改
         ⚠ 文件修改时间明显晚于程序记录（相差 376149 分钟）

场景 3  恢复原库
        status: ok | issues: 无
```

### 8.4 按股指纹（`_digests`）与自动修复

`_meta` 只能发现「文件被改过」，无法定位到具体哪只股票。因此在每个日 K 分片库里
再加一张 `_digests`，**每只股票一行**：

```sql
CREATE TABLE _digests (
  code       TEXT PRIMARY KEY,
  rows       INTEGER NOT NULL,     -- 行数
  first_date TEXT NOT NULL,
  last_date  TEXT NOT NULL,
  checksum   TEXT NOT NULL,        -- 该股**全部行情字段**的确定性 HMAC
  version    INTEGER NOT NULL,     -- 指纹算法版本，参与字段变更时 +1
  updated_at TEXT NOT NULL
) WITHOUT ROWID;
```

**参与指纹的字段**：覆盖全部行情列（含 `amount` / `turnover` / `amplitude` /
`change_pct` / `change_amount` / `adjust` / `source`），只排除 `code`（查询键）与
`fetched_at`（采集时间戳，非行情数据）。早期版本只算 6 个价格列，于是改成交额、换手率
或数据来源标记都发现不了——这是修过的一个盲区。

- **写入时刷新**：`upsert_bars` 只重算**本次涉及**的那几只股票（毫秒级），不影响批量同步效率
- **读取前校验**：`list_bars` / `load_bars` 默认先比对指纹，不一致即抛 `UntrustedDataError`，
  **绝不把可疑数据交给上层计算**
- **检测到即自动修复**：`stock_detail` 捕获后直接调用 `price_service.refetch_bars`
  **全量重抓并整体替换**，成功后用户无感（响应带 `repaired` 字段说明修复详情）

**版本号为何必需**：参与字段一变，新旧摘要就无法比对，会把**全部正常数据**误判成
「被篡改」。因此字段集合变更时必须递增 `DIGEST_VERSION`，启动时 `ensure_digests()`
自动把旧版本指纹整体升级。注意：**升级那一刻以当前数据为新基线，故无法发现升级之前的改动**——
这是不可回避的固有代价，与 `ensure_signed()` 首次补签同理。

#### 一个踩过的坑：增量写入会「洗白」篡改

`upsert_bars` 写入后会重算**整只股票**的指纹，而增量写入只覆盖「有数据的那几天」。
于是存在一条绕过路径：

```text
改历史行（此时读取会被拒绝）
  → 等一次日常同步（导入股票池每天都发生）
  → 指纹被整体重算，改动被纳入新基线
  → 从此读取一切正常，篡改**永久隐身**
```

现已在 `upsert_bars` 中改为：**写入前先判定旧指纹，已损坏则不重算**
（保留旧指纹 → 读取仍报错 → 继续触发全量重拉）。已补回归测试固化。

### 8.5 接口

```text
GET  /health                     返回 integrity 字段（启动时校验一次并缓存）
GET  /api/system/integrity       结构级校验：各库签名 / 写入时间 / 结构版本
GET  /api/system/integrity/deep  深校验：逐股重算指纹，定位不可信的个股
GET  /api/system/integrity/seal  查看密钥存放状态（是否已绑定本机）
POST /api/system/integrity/seal  把密钥改为 DPAPI 密封（绑定本机）
POST /api/system/integrity/resign 把当前状态重记为可信基线（⚠️ 会接受当前数据）
POST /api/system/rebuild         按代码**重新抓取**日K（恢复可信的正规途径）
```

**`resign` 与 `rebuild` 的区别**：`resign` 是「接受现状」（仅在清楚变动来源时用）；
`rebuild` 是「用数据源的真实数据覆盖」，因此它是恢复可信的正规手段。

**原则：不静默丢弃数据。** 数据不该由程序在用户不知情时被删除：

- 日 K 检测到不可信 → **自动全量重抓并整体替换**（**先抓取、后写入**）
- 重抓失败 → 抛错、**库中数据原样保留**，并如实报告原因
- 其余库（池快照 / 消息面 / 因子）→ **只报告**，是否重建由使用者决定

**冷却**：自动重抓要打数据源（东财不可用时还会降级腾讯，一次几秒），
同一只股票 `REFETCH_COOLDOWN_SECONDS = 60` 秒内不重复执行，避免反复刷新或批量导入
把请求放大成几百次抓取；用户点「重新抓取」（`force=True`）时跳过冷却立即执行。

### 8.6 密钥绑定本机（DPAPI，不提供恢复码）

密钥不再以明文存放在 `.env`，而是用 Windows DPAPI 密封：

```text
DATA_SECRET_SEALED=01000000d08c9ddf0115d1118c7a00c04fc297eb01000000...
```

- 密文只能被**本机 + 当前用户**解开；库文件拷到别的机器、或换主板 / 重装系统后，
  密钥无法还原 → 既有数据一律校验失败
- **按设计不提供恢复码**：既定原则是「丢数据可重拉」，解不开时重新抓取即可，
  不必为了可迁移性牺牲绑定强度
- 启动时若发现仍是明文存放，会**自动改为密封**；当前系统不支持 DPAPI 时退回明文并注明

### 8.7 一处容易自伤的坑（已修复）

`db.connect()` 原实现每次都执行 `PRAGMA journal_mode=WAL`。但在库**已经是 WAL** 时，
该 PRAGMA 依然会改写文件头——文件时间变了，却不产生 DML（`total_changes` 不变），
于是元信息时间不刷新，**每次启动都误报「被外部改动」**。

现改为「只在还不是 WAL 时切换」，并把容差放宽到 300 秒
（真被外部写入时偏差是分钟级以上，实测篡改场景相差 120 分钟，仍能稳定检出）。

### 8.8 单实例锁（同一数据目录只允许一个进程）

见 `instance_lock.py`。两个进程同时写同一数据目录会让 SQLite 的 WAL 互相打断、
指纹与签名来回覆盖（后写的把先写的当基线），属于**静默损坏**——不报错，但可信度已失。
因此必须在任何「写数据目录」的动作**之前**拦住，晚一步就已经互相污染了。

- 用**操作系统排他文件锁**（Windows `msvcrt.locking`，其他平台 `fcntl.flock`）；
  取不到即抛 `AlreadyRunningError`，启动流程打印说明并以非 0 退出码结束
- **不用「PID 文件 + 判断进程是否存在」**：进程被强杀会留下陈旧 PID，
  要么误判「已在运行」而拒绝启动，要么误判「已退出」而放行两个实例
- 锁区刻意放在内容区之后（偏移 64 KB）：Windows 文件锁是强制锁，会阻止他人读写被锁区间
- 锁**按数据目录**生效，而非按端口——因此即便改用别的端口也会被拦住

### 8.9 能力边界与取舍（诚实说明）

- HMAC **不是加密**——它保证「改了能被发现」，但不阻止读取。防的是**篡改**，不是**保密**。
  同理，改库**不需要读懂程序**：任何 SQLite 工具都能改、且一定改得成功；
  这里做的是「防篡改**检测**」，而不是「防篡改**阻止**」。
  一旦拿到 `.env` 里的密钥，就能改完数据再重算指纹——此时什么都不报。
- 本地单机形态下密钥终究在本机，**无法彻底阻止有权限的人**；
  这里的定位是「提高门槛 + 可检测」。
- `ensure_signed()` / `ensure_digests()` 会把引入本机制**之前**就存在的数据补签一次，
  因此**无法发现签名之前**已发生的改动——这是首次引入的固有限制
  （指纹算法升级时同理：升级那一刻以当前数据为新基线）。
- **数据完整 vs 数据可信的取舍**：`overwrite_bars` 在数据源只返回部分年份时，
  仍会**整体替换**（实测会删除未被覆盖的历史数据）。这是**刻意选择**——
  按第一原则，宁可整体重拉，也不保留来源存疑的数据。

**如果将来需要更彻底的保护**（多用户 / 多机部署）：
数据只留在服务端、客户端仅通过只读接口访问，配合账号体系与审计日志；
若还需「库文件落地即密文」，再叠加 SQLCipher 这类透明加密。
