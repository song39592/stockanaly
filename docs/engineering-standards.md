# 全局技术规范（展开版）

> 规则区只留判据：`.codebuddy/rules/engineering-standards.md`。本文是展开与佐例。

## 一、选实现方式的优先级

按顺序过，**前一条不满足就不必看后面**（淘汰赛，不是并列清单）：

### 1a. 规格 / 口径正确

- 问：结果对不对？偏差（幸存者 / 前视）有没有**显式声明**？
- 「能跑出结果」≠「口径对」。用今天的市值去筛 2023 年的样本：功能是实现了的，结果是错的。
- 数据源给不出的口径（历史股本、历史 ST 名单）消不掉，但**必须写进报告**，不能藏着。

### 1b. 功能可用

- 问：跑得通吗？边界 / 空值 / 异常处理得住吗？
- 空值约定要先定：返回 `None` 还是 `0`？本项目定为**一律 `None`，绝不返回 `0` / `inf`**
  （`json.dumps(inf)` → `Infinity`，不是合法 JSON，前端解析直接抛异常）。

### 2. 分层与依赖方向正确（硬约束）

- 问：依赖是单向的吗？新代码放进正确的层了吗？
- 地基错了，后面所有抽象都建在错的地方。
- 「架构完备 / 预留扩展点」属过度设计，推后甚至不做。

### 3. 可观测 + 可验证

- 问：结果能解释吗？失败能定位吗？改动有测试兜底吗？
- 「每项剔除了多少只」这类回传不是锦上添花：没有它，界面显示「剔除后 = 基池」而实跑剔掉
  一千多只，**两边都不报错**。
- 契约测试的收益不只在校验当下，还在于**让下次改口径敢做**。

### 4. 同类逻辑收敛为单一来源

- 问：同一口径有几份实现？
- 有副本 = 将来两边算出两个数、两边都不报错。

### 5. 复杂度（按场景加权）

- 全市场 5599 只的批量任务，复杂度能进第 2 位；点一下按钮的交互里它几乎无关。
- 评估要看**真实数据量**，不靠猜。例：`load_bars` 逐标的缓存、
  raw OHLCV **只取权重实际变动的 code**、`_IdxOnly` 省内存 —— 都是复杂度驱动的设计。

### 6. 代码量（约束下的最简）

- 在满足 1~5 的前提下取更简单的那个。
- 不是「越少越好」：两个方案差 20% 代码量但一个更难懂时，代码量不该当决胜项。

## 二、抽象的判据

**先分清是哪种相似**：

| 类型 | 判断 | 动作 |
|---|---|---|
| 同一逻辑被复制 N 遍（业务口径出现在多处） | 漏改一处就静默失真 | **该抽**，抽成单一来源（`formulas/`、`core/`） |
| 底层 API 长得像（同一框架调用，参数与语义各不相同） | 漏改其中一个并不产生错误 | **默认不抽**（包一层只省几行，多一层间接 + 不贴合的通用函数） |

**抽之前问一句**：这批调用点共享同一条「必须同时满足」的约束吗？
共享（都要设同一个上限 / 都要带同一个鉴权头）→ 该抽；只是形似 → 不该抽。

**还要看抽象自身的体量**：13 行小工厂 + 21 个调用点 → 值得；
200 行新层 + 80 个调用点 → 慎重（抽象不贴合时比重复更糟）。

> 抽象的收益是**消除口径漂移**，不是「少写几行」。
> 拿不出「将来哪两处会不一致」的证据，就别抽。

## 三、防守性改动：先评估实际触发条件

同一根因、多个入口时，先给**可复现的判据 + 具体数字**，不写「应该不会触发」。

- 评估结论连同「触发的代价」一起给用户；
  **跨模块的批量统一必须等用户拍板**，单模块内统一可自判但要写明结论。
- **低概率 + 高代价** → 不要默默扩散改动，也不要默默不修：写进方案交人决定。

## 四、本项目佐例

### 反例：按「统一」批量改，收益为 0

`JavaScriptSerializer.MaxJsonLength` 默认 2 MB。历史回测报告实测 **9.7 MB**（必炸），
而同页实时结果只有 0.2 MB、其它页接口 ≤ 208 KB（触发不了）
→ 结论是只改策略页那一个文件，**不做全站 81 处替换**：
后者收益为 0，却把冲突面、误伤面、review 面一起放大（还会连带拖慢每次 exe 合并）。

### 正例：小而贴合的抽象值得抽

`J.Ser()` —— 13 行小工厂 + 21 个调用点，共享同一条约束
（这一页的 payload 大小由后端决定，前端不该假设它一定小）→ 值得抽。
`NumKit.Format` 把 3 处数值格式化收敛到 1 处 → 同样值得。
⚠️ 注意：**抽象与「不要扩大改动面」是两件事**，可以同时成立 ——
真正会炸的仍只有 1 处，抽象不改变「改哪一处」的结论。

### 反例：实现欠债把改动面放大 10 倍

2026-11 一次回测范围口径优化（微盘改用「区间起点」PIT 市值）牵动 **10 个文件**，
而按分层设计本该只改 `strategies/core/universe.py` 一个。原因是三条接缝当时不存在：
① 股票池层只吐 `codes`、不吐「剔了什么」→ 波及编排 / 报告 / 前端；
② spec 构造散在路由层（预览一份、实跑一份）→ 改口径漏一处 → 界面与实跑口径不一致；
③ 范围层没有契约测试 → 口径错几个月都没人发现。

补完这三条后，「改口径 = 只动 `universe.py`」才成立
（见 `backend_fastapi/strategies/ARCHITECTURE.md` 与 `backend_fastapi/test_conventions.py`）。

### 正例：克制本身就是一种设计能力

`universe.spec_from_request(req)` 只做「把请求翻成 spec」这一件事：
没有做成 Spec 类、没有做成规则插件体系。真实需求就这么大时，
**克制比完备更值钱**。

### 反例：控件文本当传参通道 → 静默失真

`_quickSearch.Text = code` → `SelectTab()`（内部会调 `HideQuickSearch` 清空文本）→
`StockOpen()` 靠**再读一次** Text 取值 → 读到空串 → 6 位代码退化成「指标名」
→ 换指标而不是开个股，**不报错、只是没反应**。
且触发条件很窄（只在控件**可见**时才真清空）→ 「以前一直正常」，
直到接入联想下拉才炸。详见 `.codebuddy/rules/frontend-conventions.md`。
