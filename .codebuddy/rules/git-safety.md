# Git 提交与推送需明确指令

涉及 Git 的**提交（commit）**与**推送（push）**动作，必须**等待用户显式下达「提交」/「推送」等明确指令后**才能执行。不得：

- 在完成其它任务（改完代码、编译通过、修复 bug、拉取代码等）时**顺带自动提交或推送**；
- 自行判断「时机合适」而主动执行 `git commit` / `git push` / `git commit --amend`；
- 把用户模糊表述（如「保存一下」「搞定了」「好了」「收尾」）推断为提交/推送指令。

以下情况不在此限，可正常执行，无需额外确认：

- `git status` / `git diff` / `git log` / `git fetch` 等**只读**操作；
- 用户已明确说「提交」或「推送」之后，该指令所涵盖的后续步骤（例如用户说「提交并推送」，则 commit 后的 push 属于同一指令范围）。

若用户表述模糊、无法判断是否属于提交/推送指令，应先以简洁提问确认，**而不是直接执行** git commit / git push。

## 禁止提交 / 推送到 main（或 master）分支
- 任何 `git commit` / `git push` 都**不得指向 `main` / `master`** 等受保护主分支。
- 改动应先在功能分支（如 `fix/xxx`、`feat/xxx`）上提交并推送，再走 PR / MR 由人工合并到主分支。
- 若当前恰好处于 main 分支，需要先把改动迁出（新建并切换分支）后再提交/推送，不得直接在 main 上落提交或推到 main。

## 远程 base 不一致时禁止强行覆盖
- 当本地分支与远程对应分支的 **base 不同**（远程已有他人新提交，本地落后或已分叉）时，**不得**使用 `git push --force` / `--force-with-lease` 等方式强行覆盖远程历史。
- 必须先**停止并提示用户**，由人工确认后续处理（rebase 到新 base / merge / 放弃本地改动等），不得自行决定覆盖或强行推送。

## BUG 排查：先定位，后修改
- 排查 BUG 时，若**无法直接从源码静态定位根因**，必须先通过**日志（LOG）/ 诊断手段**定位：加临时日志、查看运行日志、稳定复现并采集证据，确认根因后再动手修复。
- **禁止**"直接改代码试一试、看运行结果"的试错式修改——即不得靠反复修改并运行来碰运气定位或验证。先有证据，再谈改动。

## 改动后端代码后必须先重启后端再验证
- 修改 `backend_fastapi/*.py` 等后端代码后，**验证前必须先结束正在运行的旧 uvicorn 后端进程**（占用 8000 端口的进程），再重开启动器让它用新代码重新拉起。
- 原因：启动器检测到后端已在运行会**不抢占、不重启**；若不清旧进程，验证测到的仍是旧代码，结论失真，会误判优化/修复是否生效。

## 临时诊断代码必须验证后立即清理
- 加临时诊断（前端 `Log` 标签、后端落盘 trace / `print` 等）时，必须标注"待清理"，并在验证通过后**立即删除、再提交**。
- 不得把诊断代码随业务修复长期留存；涉及前端（需重编译 `stockpool.exe`）的诊断，更不得将"调试版"当"发布版"提交。

## 提交只 add 明确改动的文件
- 提交时只 `git add` 本次明确要提交的文件，**禁止** `git add -A` / `git add .` 等一次性暂存，以免把诊断残留、本地配置、调试版 exe 等无关改动顺手提交。
- 注意：`stockpool.exe` 等**发布版生成物属于应当提交的范畴**（见下条），不得仅因其为生成文件就排除在提交之外。

## 不明确指令先给方案，不直接改
- 当用户的指令存在**歧义、信息不足，或我不确定其真实意图**时，必须先**提供方案 / 澄清问题**，经用户确认后再动手修改代码或执行变更动作。
- 不得仅凭推测直接修改文件或执行变更（包括但不限于改代码、改配置、执行命令、提交/推送等）。先对齐，再行动。

## 生成物（.exe）也需提交，但只提交发布版
- `stockpool.exe` 等编译产物虽是生成文件，但按本项目约定**需要纳入版本控制并提交**，以便其他设备直接运行、无需再编译一次。
- 提交时应包含经确认的正常**发布版** `stockpool.exe`；**禁止**提交"调试版 / 含临时诊断"的 exe（此类属于"临时诊断"清理范围，不得入库）。
- 若本次改动涉及前端代码并重新编译了 exe，需确认编译的是干净发布构建后再一并提交，既不能遗漏，也不能用调试构建顶替发布版。
