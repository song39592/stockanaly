# 规则与说明文件的同步纪律

## 一、为什么有这条规则

没有同步约束的实测后果（本项目真实发生过）：

- 根 `README.md` 的目录树写着 `股票池追踪系统.exe`、顶层 `chip_routes.py`，
  而产物早已改成 `stockpool.exe`、真实现早已搬进 `features/` ——
  **最常被读的文件，恰恰是最不新的**。
- `docs/requirement.md` 仍让读者去 `market-sector.html` 找盘面页，
  而该页早已删除并迁进 launcher 原生页；整个需求文档里没有指标、策略回测、筹码、
  历史下载、RPS 池这些已上线功能。
- `docs/CONTRIBUTING.md` 写「验证后合并到 main」，`git-workflow.md` 写「禁止提交/推送到 main」——
  不是重复，是**矛盾**，读哪份都会走偏。

根因不是「忘了改」，是**没有把「改代码时必须同步哪些文档」写进会被强制想起的地方**。
规则区是唯一常驻加载的地方，所以约束必须写在这里。

## 二、分层：谁说了算

| 位置 | 定位 | 判定标准 | 同步触发 |
|---|---|---|---|
| `.codebuddy/rules/*.md` | **纪律 + 指针** | 「做错就会出错，且不查就会犯」 | 约定变更 |
| `docs/*.md` | **展开细节** | 「偶尔查一次，抄错当场就看出来」 | 对应领域变更 |
| `docs/changelog.md` | **历史流水** | 只追加、不改写 | 每次发布 |
| `docs/archive/` | **一次性记录** | 已完成，不是现行规范 | 不主动更新 |
| 根 `README.md` | 项目介绍 + 快速启动 | 给新来的人 | 启动方式 / 目录结构 |

**容量纪律（硬约束）**：规则区**常驻加载**，每条规则都占用每个会话的上下文。
因此规则文件只放「纪律」与「指针」，**不放展开细节**。

- 规则区总量控制在 **2.8 万字符以内**；单文件不超过 **8 千字符**。
  超出就要问：「这段内容是纪律，还是可以挪到 docs 的细节？」
- 典型反例：把 `docs/database.md`（1.7 万字符的表结构）搬进规则区 ——
  它不会被「想起」，只会稀释旁边真正重要的纪律（如「改了指标必跑 golden --update」）。
  正确做法是规则里只留一行指针 + 一张「有哪些库、哪些表」的精简清单。
- 超出上限时**先做减法**：优先删重复表述（同一事实的两处副本）、其次删展开细节，
  **不要**靠调大上限来过关 —— 上限是防线，调大它等于拆防线。

## 三、同一事实只有一处权威

判定法：同一个事实出现在 N 个地方时，先问「**改它时会不会漏改其中一处？**」

- 会漏 → 必须收敛成**一处权威**，其余位置只写指针。
- 不会漏（各处本就独立、抄错当场能看出来）→ 可以并存。

收敛后的指针写法（照此办理）：

- ✅ `表结构详见 docs/database.md` + 一张精简清单
- ❌ 在规则里复制整张表结构（= 多一份会过期的副本）

**注意**：把「事实」收敛到一处，不代表把「展开」也收敛到一处。
权威处写全，其余处写「详见 X」—— 这是**分层**，不是重复。

## 四、触发矩阵：改 X 必须同步 Y

| 你改了什么 | 必须同步 | 漏了会怎样 |
|---|---|---|
| 目录结构 / 模块职责 / 权威位置 | `rules/project-structure.md` + 根 `README.md` 目录树 | 新会话读错位置、扫错代码 |
| 新增 / 移除 / 重命名功能 | `docs/requirement.md` | 需求文档与实现分叉 |
| 数据库表结构 / 列语义 | `docs/database.md` | 同上 |
| 后端接口的字段 / 返回结构 | `backend_fastapi/README.md` + `launcher/*.cs` 消费端 | 前端读到旧字段**静默降级**（不报错，最难发现） |
| 后端接口的路径前缀 | `rules/project-structure.md` 路由前缀表 + 启动器探测地址 | 启动器探不到服务 |
| 数据目录 / 日志 / 清理约定 | `core/config.py`、`core/storage.py`、`core/logutil.py` 的注释（权威）→ `backend_fastapi/README.md` 只留指针 | 说明文件变成会过期的副本表 |
| 指标 / 策略 / 筹码公式的计算逻辑 | `indicators/_golden.json`（跑 `golden --update`） | `test_indicators_golden` 失败 |
| 规则 / 约定本身 | 对应 `rules/*.md` + 本文第二节的「容量纪律」 | 规则与现状脱节、规则区越写越大 |
| `launcher/*.cs`（新增/删除顶层文件） | `build_exe.bat` 清单 + 重跑生成 `stockpool.exe` | 新类不进 exe（「改了没生效」） |
| 分发单元 | `rules/cross-device-portability.md` | 目标设备缺文件 |

## 五、怎么发现漏同步（不要只靠记）

`scripts/check-docs.ps1` 做机器能做的部分：

- 扫 `*.md` 里提到的**仓库内路径**，检查文件/目录是否还存在 → 抓出「文档说的位置已经不存在」。
- 扫 `*.md` 里提到的**接口路径前缀**，与后端 `APIRouter(prefix=...)` 实际值比对 → 抓出「前缀漂移」。
- 检查规则区字符总量是否超上限 → 抓出「规则区膨胀」。

退出码 `0` = 通过（可能仍有 WARN 待确认项），`1` = 有硬错误（FAIL，逐条打印）。改动文档后跑一遍。

机器查不出的部分仍要靠人：**语义是否准确**（比如 requirement 里描述的交互是否还成立）。
自检脚本只能证明「路径还在」，不能证明「描述还对」。

## 六、改文档时的自检清单

1. 这条内容**属于纪律还是细节**？纪律 → 规则区；细节 → docs。
   规则区已有同样内容时，**改那一份**，不要新建。
2. 是否制造了**第二处权威**？有 → 收敛成指针。
3. 规则区总量是否仍在 2.8 万字符内、单个文件 8 千字符内？
4. 改动是否触及上表的某一行？是 → 逐项同步到位。
5. 跑 `scripts/check-docs.ps1`。
6. 文档里提到的路径，是否都是**真实存在**的？（不要写「大概在某处」）
