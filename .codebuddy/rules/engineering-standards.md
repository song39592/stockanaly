# 全局技术规范

> 展开版与本项目佐例：`docs/engineering-standards.md`。本文只留判据。

## 一、选实现方式的优先级

按顺序过，**前一条不满足就不必看后面**（这是淘汰赛，不是并列清单）：

| 序 | 维度 | 判据（问自己） |
|---|---|---|
| 1a | **规格 / 口径正确** | 结果对不对？偏差（幸存者、前视）有没有**显式声明**？ |
| 1b | **功能可用** | 跑得通吗？边界 / 空值 / 异常处理得住吗？ |
| 2 | **分层与依赖方向正确** | 依赖是单向的吗？新代码放进正确的层了吗？（硬约束） |
| 3 | **可观测 + 可验证** | 结果能解释吗？失败能定位吗？改动有测试兜底吗？ |
| 4 | **同类逻辑收敛为单一来源** | 同一口径有几份实现？（有副本 = 将来两边算出两个数、两边都不报错） |
| 5 | **复杂度**（按场景加权） | 数据量大的场景可上移到第 2 位；单次交互可忽略 |
| 6 | **代码量**（约束下的最简） | 在满足 1~5 的前提下，取更简单的那个 |

- **1a 与 1b 必须分开**：「能跑出结果」≠「口径对」—— 用今天的市值去筛历史样本，
  功能是实现了的，结果是错的。
- **2 是硬约束**：地基错了，后面所有抽象都建在错的地方。
  「架构完备 / 预留扩展点」属过度设计，推后甚至不做。
- **5 按场景加权**：全市场 5599 只的批量任务，复杂度能进第 2 位；
  点一下按钮的交互里它几乎无关。评估要看**真实数据量**，不靠猜。
- **6 不是「越少越好」**：两个方案差 20% 代码量但一个更难懂时，代码量不该当决胜项。

## 二、第 4 条：抽象的判据

**先分清是哪种相似**：

- **同一逻辑被复制了 N 遍**（业务口径出现在多处）→ **该抽**，抽成单一来源
  （`formulas/`、`core/`）。
- **底层 API 长得像**（同一框架调用，参数与语义各不相同）→ **默认不抽**：
  包一层只省几行，却多一层间接 + 一个不贴合的通用函数。

**抽之前问一句：这批调用点共享同一条「必须同时满足」的约束吗？**
- 共享（如「都要设同一个上限」「都要带同一个鉴权头」）→ **该抽**：
  约束从 N 处降到 1 处，漏改风险同比例下降。
- 只是形似、各自独立（漏改其中一个并不产生错误）→ **不该抽**。

**还要看抽象自身的体量**：新增多少行、改多少个调用点。
13 行小工厂 + 21 个调用点 → 值得；200 行新层 + 80 个调用点 → 慎重
（抽象不贴合时比重复更糟）。

> 抽象的收益是**消除口径漂移**，不是「少写几行」。
> 拿不出「将来哪两处会不一致」的证据，就别抽。

## 三、防守性改动：先评估实际触发条件

同一根因、多个入口时，先给**可复现的判据 + 具体数字**（实测响应体大小 / 数据量上限 /
代码里的硬阈值），不写「应该不会触发」。

- 评估结论连同「触发的代价」一起给用户；**跨模块的批量统一必须等用户拍板**，
  单模块内统一可自判，但要在方案里写明评估结论。
- **低概率 + 高代价** → **不要默默扩散改动，也不要默默不修**：写进方案交人决定。
- 「抽象 / 收敛」与「不要扩大改动面」是两件事，可以同时成立 ——
  真正会炸的地方仍可能只有 1 处，抽象不改变「改哪一处」的结论。
