# Git 工作流纪律

> 「提交 / 推送要不要授权、推送前自检」与「分支怎么起、怎么命名、什么时候删」都在本文。

## 一、提交与推送必须获明确指令

涉及 Git 的**提交（commit）**与**推送（push）**，必须**等待用户显式下达「提交」/「推送」等明确指令**后才能执行。不得：

- 在完成其它任务（改完代码、编译通过、修复 bug、拉取代码等）时**顺带自动提交或推送**；
- 自行判断「时机合适」而主动执行 `git commit` / `git push` / `git commit --amend`；
- 把用户模糊表述（如「保存一下」「搞定了」「好了」「收尾」）推断为提交 / 推送指令。

不在此限、可正常执行：**只读**操作（`git status` / `diff` / `log` / `fetch`）；
以及用户已明确说「提交」或「推送」之后、该指令所涵盖的后续步骤
（例如说「提交并推送」，则 commit 后的 push 属同一指令范围）。

表述模糊、无法判断时 → **先简洁提问确认**，不要直接执行。

## 二、分支规范

### 命名
- 格式 `<类型>/<短描述>`，类型白名单：`feat` `fix` `refactor` `docs` `chore` `perf` `test`。
- 短描述用 **kebab-case**、不超过 6 个词，说清「改什么」；不写编号、不写日期。
- 禁止：工具名 / 机器名前缀（`codex/`、`claude/`）、无类型前缀（`dev`）、中文、空格、下划线。
  历史遗留的 `codex/settings-download-fixes`、`dev` 这类在清理时一并收掉。

### 一类改动 = 一个分支
- **一次独立任务 = 一个分支**：文档 / 规则体系的任务走 `docs/xxx`，代码任务走
  `fix|feat|refactor/xxx`。不要把「顺手改的文档」和「功能修复」混在一个分支里 ——
  一个 PR 装两件事，审的人看不出重点。
- **必要配套除外**：某次改动**必然**牵连的说明同步（改了行为就要改说明、规则里明确要求
  同步的那些文件）跟该改动同支 —— 配套同步脱离代码后，文档描述的是**尚不存在**的功能。
  例：改了 `launcher/*.cs` 就要同步 `README.md` 的启动说明。
- 中途发现另一件事 → **另开分支**，不要顺手带上。
- 分支从**当前主线**（`origin/main`）切出，不要从别的功能分支切 —— 叠罗汉会让 base 对不上。

### 起停时机
- **动手改之前**就建分支，不要在 `main` 上直接改。
- 本地创建即可；**推送需要明确指令**（见第一节）。

### 生命周期：合并完就删
- 分支合并进 main 后：**本地分支和远端分支都要删**
  （`git branch -d <name>` / `git push origin --delete <name>`）。
- 留着已合并的分支只会让 `git branch -a` 刷屏、让人分不清哪个是活的。
- 定期清一遍：`git branch --merged origin/main` / `git branch -r --merged origin/main`，
  逐个确认后删。**删远端分支前先确认没有别人的 PR 挂在上面**。
- ⚠️ **删分支不丢东西**（内容已在 main 里）；唯一例外是「还没合并就想放弃」—— 先确认内容不要了。

## 三、禁止推送到主分支

- 任何 `git commit` / `git push` 都**不得指向 `main` / `master`** 等受保护主分支。
- 改动先在功能分支上提交并推送，再走 PR / MR 由人工合并到主分支。
- 若当前恰好处于 main 分支：先把改动迁出（新建并切换分支）再提交 / 推送。

## 四、远程 base 不一致时禁止强行覆盖

- 本地分支与远程对应分支的 **base 不同**（远程已有他人新提交，本地落后或已分叉）时，
  **不得**使用 `git push --force` / `--force-with-lease` 覆盖远程历史。
- 必须先**停止并提示用户**，由人工确认后续处理（rebase / merge / 放弃本地改动），
  不得自行决定覆盖或强行推送。

## 五、推送前：改动影响面自检

执行 `git push` 前先做一遍自检：本次推送包含的**全部提交**
（`git log <远程分支>..HEAD`，而不只是最后一次改动）是否对其它模块、架构产生了**未处理**的影响。

本节只负责「**按改动路径触发对应清单，并确认那些清单都做过了**」，不重复其它规则的内容。

- **① 对其它模块的影响（按改动路径对照）**
  - 改了 `backend_fastapi/core/` 下的**单一来源**模块（`bars_schema.py` /
    `registry_scan.py` / `formulas/`）→ 回到所有引用点确认：两侧是否都自动生效、
    有没有旁路复制了一份口径。
  - 改了 `bars_schema.py` 的日线标准列 → 新增「价」量纲的列必须同时进 `PRICE_SCALED_COLUMNS`。
  - 改了指标 / 策略 / 筹码公式的**计算逻辑** → 已跑 `python -m indicators.golden --update`，
    且 `_golden.json` 一并提交。
  - 改了后端接口的**字段 / 返回结构** → 前端 `launcher/*.cs` 已同步；只改后端不改前端，
    前端会读到旧字段**静默降级**（不报错，最难发现）。
  - 改了 `launcher/` 顶层 `.cs`（新增 / 删除）→ `build_exe.bat` 清单已同步。
  - 改了 `launcher/*.ps1`、后端入口或分发文件清单 → 目标设备需重新拷贝整个目录，
    交付说明写清「只换 exe 等于没换」。
  - 改了数据库表结构 / 列语义 → `docs/database.md` 已同步。
- **② 对工程 / 模块架构的影响**
  - 依赖方向是否被打破；共用内核有没有被塞进 `chipformulas/core/`；
    `indicators/` 下的非指标模块有没有漏进 `_EXCLUDE`。
  - 有没有新造第二套口径 / 第二份常量的副本 —— 有副本 = 将来两边算出两个数、两边都不报错。
  - 有没有让原本「单一来源」的东西变成多处维护。
  - 有没有改变模块间的职责边界 → 受影响的一方是否已同步。
- **③ 规则文件是否要同步**
  - 只有**实质性变化**才改，避免噪音（规则文件是常驻加载的，改一次影响后续所有会话）。
  - 触发条件：① 改 `core/` 单一来源模块 → `project-structure.md`；② 改构建 / 分发 / 安装方式
    → `cross-device-portability.md`；③ 改插件包注册契约 → `backend-conventions.md`；
    ④ 新增 launcher 顶层类或改「一个主类一个文件」约定 → `project-structure.md`；
    ⑤ 本次踩到的新坑值得沉淀 → 写进对应规则文件（别只留在代码注释里）。
- **④ 结论与动作**
  - 结论要落到**具体文件**：哪些受影响、是否已处理、规则文件要不要改。
  - 发现未处理的影响 → **先停下来报告**并给处理建议，**不擅自推送**；
    规则文件要不要改由用户确认（改规则 = 改工程约定）。
  - 全部通过 → 再执行 `git push`。

## 六、提交纪律

- **只 add 明确改动的文件**，**禁止** `git add -A` / `git add .`，以免把诊断残留、
  本地配置、调试版 exe 等无关改动顺手提交。
- **生成物（`.exe`）也要提交，但只提交发布版**：`stockpool.exe` 按本项目约定纳入版本控制
  （便于别的设备直接跑）。⚠️ **禁止**提交"调试版 / 含临时诊断"的 exe。
  涉及前端代码并重编 exe 时，确认是干净发布构建后再一并提交 —— 既不能遗漏，
  也不能用调试构建顶替发布版。
- **临时诊断代码必须验证后立即清理**：前端 `Log` 标签、后端落盘 trace / `print` 等，
  标注「待清理」，验证通过后**立即删除、再提交**。
- **不明确指令先给方案，不直接改**：指令有歧义或信息不足时，先给方案 / 澄清问题，
  经确认后再动手（含改代码、改配置、执行命令、提交 / 推送）。不得仅凭推测执行变更。
